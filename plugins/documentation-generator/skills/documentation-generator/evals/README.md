# Evaluation suite

Fourteen evaluations covering every document type the skill produces and the
edge cases where documentation generators typically fail — fabricating a schema
for a service with no database, describing stubs as if they work, padding a
three-file project into twenty pages.

```
evals/
  evals.json          the suite — objectives, prompts, assertions, pass criteria
  make_fixtures.py    generates nine purpose-built repositories
  run_evals.py        prepares runs and emits the task prompts
  grade_evals.py      grades outputs, writes grading.json, prints a summary
  lib/checks.py       the declarative check library
  fixtures/           generated (git-ignorable)
  workspace/          run outputs (generated)
```

---

## Quick start

```bash
cd .claude/skills/documentation-generator/evals

python make_fixtures.py            # write the nine fixture repos
python run_evals.py --list         # see what the suite covers
python run_evals.py --all          # prepare runs, print the task prompts
# … execute those prompts, saving outputs where each one says …
python grade_evals.py --iteration iteration-1
```

Exit codes from `grade_evals.py`: `0` everything passed, `2` something failed,
`1` nothing to grade. That makes it usable in CI.

### Running a subset

```bash
python run_evals.py --only e06 e09          # the two honesty edge cases
python run_evals.py --tag EDGE              # every edge case
python run_evals.py --only e11              # auth documentation
python run_evals.py --all --with-baseline   # also emit no-skill prompts
```

`--with-baseline` produces a second prompt per eval with no skill attached.
Grade both and compare — that is how you tell whether a change to the skill
actually improved anything, rather than the model having a good day.

## What each evaluation tests

| ID | Name | Type | What it is really testing |
|---|---|---|---|
| e01 | schema-doc-backend | Database Schema | Constraints explained as **business rules**, cascades documented, model/migration name divergence caught |
| e02 | api-contracts-backend | API Contracts | Every endpoint, methods, lifecycle transitions, error cases |
| e03 | architecture-backend | Architecture | Layering and **reasoning**, not a directory listing; the ledger call outside the transaction |
| e04 | sequence-flow-doc | Sequence / Flow | Transaction boundary, ordering, non-idempotent charge, committed-order-without-payment window |
| e05 | frontend-only-doc | Frontend | React/TS/Vite stack, routing, state, API layer — **without inventing a backend** |
| e06 | no-database-honesty | **EDGE** | Must not fabricate tables for a stateless service. Hard fail. |
| e07 | minimal-api-proportionality | **EDGE** | Two endpoints get a short document. Padding is the failure. |
| e08 | monorepo-structure | **EDGE** | Three packages and the shared-types contract between them |
| e09 | incomplete-project-honesty | **EDGE** | Separates working code from `NotImplementedError` stubs. Hard fail on describing the solver as functional. |
| e10 | mixed-stack-coverage | **EDGE** | Python + Node + Go as one system; the lost-job failure mode |
| e11 | auth-authorization-doc | Auth | Five roles, rank ladder, policy layer, no-self-approval, and the unchecked `typ` claim |
| e12 | repo-analysis-detection | Analysis | Detects the stack and proposes the right document set |
| e13 | full-set-backend | Multiple | Three documents, consistent style, cross-referenced |
| e14 | update-existing-document | Maintenance | Edits the build script and rebuilds rather than hand-editing the `.docx` |

Every eval runs against a fixture repository generated by `make_fixtures.py`,
so the suite works in a bare checkout with no external repositories.

### The fixtures

```bash
python make_fixtures.py --list
```

| Fixture | Why it exists |
|---|---|
| `backend-only` | Real schema, business-rule CHECK constraints, deliberate model/migration drift |
| `frontend-only` | React with no server anywhere |
| `no-database` | Stateless — a schema document would be a fabrication |
| `minimal-api` | Two endpoints; tests proportionality |
| `monorepo` | Three packages with a shared contract |
| `incomplete` | Stubs that raise; tests honesty |
| `mixed-stack` | Python + Node + Go around a Redis queue |
| `auth-heavy` | Five roles, a rank ladder, a real token flaw |
| `flow-heavy` | Checkout with an explicit transaction boundary |

Each is small enough to read in full. When an assertion fails you can see why
in thirty seconds rather than spelunking a real codebase.

**The defects are deliberate.** The constraint-name divergence in
`backend-only`, the unchecked `typ` claim in `auth-heavy`, the missing
dead-letter queue in `mixed-stack` — these are planted so the suite can measure
whether the documenter *finds* things, not just whether it describes them.

## How grading works

Each eval declares `pass_criteria`:

```json
"pass_criteria": {
  "required": ["docx_produced", "e06-no-fabricated-schema"],
  "min_score": 0.80
}
```

- **`required`** — every one must pass. One failure fails the eval regardless
  of the score. Reserve these for things that make a document *wrong*: a
  fabricated schema, a missing artefact, a false claim.
- **`min_score`** — the fraction of all assertions that must pass.

Both must hold. The split matters: `required` catches wrongness, `min_score`
catches thinness, and neither alone is sufficient. A document can be 90%
complete and still fabricate a table.

### Reading the output

```
eval                      config          score        reason
e06 no-database-honesty   with_skill      0/7   FAIL   required assertion(s) failed: …

e06 no-database-honesty [with_skill] — failed assertions:
    e06-no-fabricated-schema  HARD FAIL — does not invent tables …
                              → unexpectedly present: ['CREATE TABLE', 'primary key']
```

The evidence line is the point. It says *what* was found, not just that
something was wrong, so you can tell a genuine failure from a bad assertion.

## Comparing against a baseline

```bash
python run_evals.py --all --with-baseline
# execute both sets
python grade_evals.py --iteration iteration-1
```

Both configurations are graded against identical assertions. Two things worth
knowing when you read the comparison:

**An assertion that passes in both configurations is not measuring the skill.**
It may still be worth keeping as a regression guard, but it tells you nothing
about whether the skill helps. When most assertions pass in both, the honest
conclusion is that the model is doing the work and the skill is contributing
form rather than substance.

**Assertions measure form and coverage, not insight.** Whether a document found
the *right* things and explained them well is a judgement call. Read the
documents. The score is a floor, not a verdict.

## Extending the suite

### Adding an evaluation for an existing document type

Add an entry to `evals` in `evals.json`. Nothing else changes.

```json
{
  "id": "e15",
  "name": "graphql-schema-doc",
  "doc_type": "API Contracts",
  "objective": "Document a GraphQL schema rather than REST endpoints.",
  "repo": {"fixture": "graphql-api", "characteristics": "…"},
  "prompt": "document the graphql api",
  "expected_output": "…",
  "assertions": [
    "docx_produced", "md_mirror", "cover_and_contents",
    {"id": "e15-types", "text": "Covers every root type",
     "check": {"type": "coverage", "terms": ["Query", "Mutation"],
               "min_fraction": 1.0}}
  ],
  "pass_criteria": {"required": ["e15-types"], "min_score": 0.8}
}
```

Reference a shared assertion by name; write a bespoke one inline. See the
available checks with:

```bash
python grade_evals.py --list-checks
```

### Adding a new document type to the skill

1. **Add a fixture** if no existing one exercises it — a new entry in
   `FIXTURES` in `make_fixtures.py`. Keep it small and give it a defect worth
   finding.
2. **Add one or two evals** — a positive case and an edge case. The edge case
   is the valuable one: what would a lazy generator get wrong here?
3. **Reuse the shared assertions** for format, and write specific ones for
   content.
4. Run `--only <new-id>` until it passes for the right reasons — check the
   evidence strings, not just the verdict.

### Adding a new check type

Only when you need a genuinely new *kind* of question answered. Most content
requirements are expressible with `coverage`, `matches_all`, `matches_any` and
`absent`.

Add the function to `lib/checks.py`, register it in `CHECKS`, and give it a
one-line docstring — `--list-checks` reads it.

```python
def cross_references(d, min=2, **_):
    """Documents in the set reference one another."""
    n = len(re.findall(r"see (the )?[A-Z][\w-]+ document", d["text"], re.I))
    return n >= min, f"{n} cross-references (need {min})"
```

Every check returns `(passed, evidence)`. **Make the evidence specific** —
counts, filenames, the pattern that missed. A failing check with vague evidence
costs more time than no check at all.

## Maintenance notes

**Fixtures are generated, not committed.** Nine repos as one file of literals
stays readable; four hundred files in version control does not. Regenerate with
`python make_fixtures.py`, or `--clean` to remove them.

**Assertions drift as the skill improves.** When one starts passing in every
configuration, it has stopped discriminating — either tighten it or retire it.
`grade_evals.py --json` gives per-assertion results for tracking this across
iterations.

**Regex assertions are approximations.** `matches_any` on a handful of phrasings
will occasionally miss a document that said the right thing differently. When an
assertion fails, read the evidence and the document before assuming the skill
regressed — sometimes the assertion is what needs fixing.

**Keep hard fails rare.** They are for genuine wrongness: fabricated schemas
(`e06`), false claims about stubs (`e09`), missing deliverables. If everything
is required, one soft miss fails a run that was actually fine, and the suite
stops being trusted.

**The suite does not measure insight.** It cannot tell you whether the document
explained a transaction boundary *well*. Use it as a floor — everything below
this line is broken — and read the documents for everything above it.
